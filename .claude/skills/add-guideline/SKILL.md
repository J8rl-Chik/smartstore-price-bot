# 지침 추가 절차

`CLAUDE.md`는 세션이 시작될 때마다 로드되는 정적 맥락이다. 길어지면 핵심 지침까지 무시되므로 **넣는 것보다 넣지 않는 판단**이 중요하다.

## 1. 추가할 만한 지침인지 확인한다

아래 중 하나에 해당할 때 추가한다.

- 사용자가 직접 추가를 요청했다. (이 경우에도 아래 삭제 기준 질문을 거치고, 통과하지 못하면 추가 여부를 사용자에게 묻는다.)
- Claude가 같은 실수를 두 번째 반복했다.
- 코드 리뷰에서 "프로젝트 규칙을 미리 알았어야 한다"는 지적이 나왔다.
- 이전 세션에서 한 교정·설명을 대화창에서 다시 반복하고 있다.

새 줄을 쓰기 전에 **"이 줄을 삭제하면 Claude가 실수를 저지를 것인가?"**를 묻는다. 실수하지 않을 내용이면 조용히 빼지 말고, "이 줄이 없어도 실수하지 않을 것 같은데 그래도 추가할까?"라고 먼저 묻는다.

### 포함할 것과 제외할 것

| ✅ 포함해야 할 내용 (Include)                                                                                                                                                  | ❌ 제외해야 할 내용 (Exclude)                                                                                                   |
| ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------- |
| Claude가 스스로 추정할 수 없는 **Bash 명령**<br>예: `pnpm test:unit --runInBand` (DB 충돌로 병렬 실행 금지), `docker compose up -d db` 후에만 통합 테스트 가능                 | 코드를 읽어서 쉽게 파악할 수 있는 모든 내용<br>예: "`user.ts`는 유저 모델이다", `package.json`에 이미 있는 스크립트 목록        |
| 언어 기본값과 다른 **고유 코드 스타일 규칙**<br>예: `import` 대신 `require` 사용, 들여쓰기 2칸, 세미콜론 생략                                                                  | 표준 언어 컨벤션 및 일반 문법 지식<br>예: 변수는 camelCase, 클래스는 PascalCase, `const`를 우선 사용한다                        |
| **테스트 실행 방법 및 선호하는 테스트 러너**<br>예: `vitest` 사용, 파일 하나만 돌릴 때는 `pnpm vitest run src/core/score.test.ts`                                              | 상세한 API 문서 (외부 링크로 대체)<br>예: 엔드포인트별 요청·응답 스키마를 복사해 붙이는 대신 `API 명세: docs/api.md 참고` 한 줄 |
| **리포지토리 에티켓** (브랜치명, PR 규칙)<br>예: 브랜치명 `feat/이슈번호-요약`, 커밋 제목은 한글 50자 이내, PR은 `main`이 아닌 `develop`으로                                   | 자주 변경되는 동적 정보<br>예: 이번 주 TODO, 현재 진행 중인 작업, 의존성 버전 번호                                              |
| 프로젝트 특화 **아키텍처 결정 사항**<br>예: 비즈니스 로직은 `core/`, 외부 연동은 `adapters/`에 둔다. `core/`는 `adapters/`를 import하지 않는다                                 | 장문의 튜토리얼이나 긴 설명문<br>예: Express 라우팅 동작 원리, 미들웨어 개념 설명                                               |
| **개발 환경 특이사항** (필수 환경변수 등)<br>예: `.env`에 `DATABASE_URL` 필요, Node 20 이상, 로컬 DB 포트는 5433                                                               | 파일별 상세 설명 목록<br>예: `src/` 아래 모든 파일에 대한 한 줄 설명 표                                                         |
| 자명하지 않은 **주의사항(Gotchas) 및 동작**<br>예: `quiz.score`는 DB 트리거가 갱신하므로 코드에서 직접 수정하지 않는다, `/api/result`는 캐시되므로 테스트 시 `?nocache=1` 필요 | "깨끗한 코드를 작성하라"와 같은 당연한 일반론<br>예: "가독성을 높인다", "에러 처리를 잘한다"                                    |

## 2. 넣을 위치를 정한다

핵심 기준은 **"어떤 작업을 하든 적용되는가, 특정 작업이나 파일일 때만 적용되는가"**다.

| 지침의 성격                                        | 위치                                            |
| -------------------------------------------------- | ----------------------------------------------- |
| 항상 지켜야 하고 팀이 공유하는 명령·규칙·금지 사항 | `./CLAUDE.md` (또는 `./.claude/CLAUDE.md`)      |
| 나만 쓰는 로컬 샌드박스 URL, 개인 테스트 데이터    | `./CLAUDE.local.md` (`.gitignore`에 등록)       |
| 모든 프로젝트에 적용할 개인 선호                   | `~/.claude/CLAUDE.md` 또는 메모리               |
| 가끔 쓰는 도메인 지식, 여러 단계의 절차            | `.claude/skills/<이름>/SKILL.md`                |
| 특정 파일군에만 해당하는 지침                      | `.claude/rules/<이름>.md` + 프론트매터 `paths:` |

- **금지·"~하지 않는다" 류는 `CLAUDE.md`에 넣는다.** 스킬은 설명이 현재 작업과 맞을 때만 로드되므로 범위 밖의 행동은 막지 못한다.
- `CLAUDE.md`에는 모든 세션에 공통인 핵심 규칙만 둔다. 길어지는 절차는 스킬이나 경로 지정 규칙으로 분리하고, `CLAUDE.md`에는 한 줄 요약과 위치만 남긴다. (`@` 임포트로 파일을 나눠도 불러온 내용은 항상 로드되므로 길이는 줄지 않는다.)
- 기존 스킬의 설명이 이미 그 작업을 다루면 새 스킬을 만들지 않고 **기존 스킬에 추가**한다.
- 어느 쪽인지 정말 모호하면 추측하지 말고 사용자에게 먼저 묻는다.

경로 지정 규칙은 특정 파일을 다룰 때만 로드된다.

```
---
paths:
  - "src/api/**/*.ts"
---

규칙 내용
```

## 3. 중복·충돌을 확인한다

넣기 전에 `CLAUDE.md`, `.claude/skills/*/SKILL.md`, 메모리 인덱스를 읽고 확인한다.

- 같은 내용이 이미 있으면 새로 추가하지 않고 기존 항목을 고친다.
- 기존 지침과 충돌하면 어느 쪽을 따를지 사용자에게 묻는다.
- 틀린 것으로 드러난 기존 지침이나 구버전 지침은 지우거나 고친다.

## 4. 작성 원칙

- **구체적이고 검증 가능하게 쓴다.**
  - `✕ 코드 포맷을 잘 맞춘다` → `○ 2칸 들여쓰기를 쓴다`
  - `✕ 변경 사항을 테스트한다` → `○ 커밋 전에 npm test를 실행한다`
  - `✕ 파일 구조를 정리한다` → `○ API 핸들러는 src/api/handlers/에 둔다`
- **분량을 지킨다.** 파일당 200줄 이하를 목표로 한다. 넘길 것 같으면 분리를 먼저 제안한다.
- **구조화한다.** 대상 파일의 기존 구조와 어미(`~한다`)에 맞춘다.
- **이유를 한 줄 덧붙인다.** 경계 사례를 판단할 수 있게 한다.
- **`IMPORTANT`는 아껴 쓴다.** Claude가 특정 지침을 지속적으로 건너뛸 때만 그 줄에 붙인다.

## 5. 반영 후 보고한다

- 바꾼 위치를 파일명과 줄 번호까지 적고(예: [CLAUDE.md:12](CLAUDE.md#L12)), 왜 그 위치인지 한두 줄로 밝힌다.
- 사용자가 직접 확인하도록 안내한다. 아래 명령은 Claude가 대신 실행하지 않고 사용자에게 안내만 한다.
  - `/context`: 지침이 제대로 로드됐는지 확인
  - `/doctor prompt-audit`: 모순되거나 오래된 규칙 점검
- 지침 변경은 바로 커밋하지 않고 커밋할지 먼저 묻는다.
