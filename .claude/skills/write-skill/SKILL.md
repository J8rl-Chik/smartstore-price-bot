# 스킬(SKILL.md) 작성 가이드

스킬은 **"어떻게(How) 작업을 수행하는가"**를 담은 재사용 가능한 절차·워크플로 모듈이다. 같은 지침이나 체크리스트를 대화에 반복해서 붙여넣거나, CLAUDE.md의 정적 규칙이 절차 지식으로 길어졌을 때 스킬로 만든다.

**왜 스킬인가:** CLAUDE.md는 세션 시작 때 항상 로드되지만, 스킬 본문은 호출될 때만 컨텍스트에 올라온다. 항상 필요하지 않은 긴 절차는 스킬로 빼야 토큰이 절약된다.

## description 작성 (가장 중요)

Claude는 스킬 본문을 읽기 **전에** description만 보고 호출 여부를 정한다. 매칭에 실패하면 본문이 아무리 좋아도 쓰이지 않는다. 그래서 소극적으로 쓰지 말고 **공격적이고 구체적으로** 쓴다. 아래 3단계를 모두 넣는다.

1. **동사 나열:** 스킬이 실제로 하는 동작(작성, 검증, 분리, 디버깅 등)을 다양하게 적는다.
2. **트리거 상황:** "~할 때 반드시 참고한다"처럼 직접적인 조건과 사용자가 실제로 칠 법한 표현·동의어를 따옴표로 함께 적는다. 사용자가 스킬 이름을 말하지 않아도 발동해야 하는 상황이면 그렇게 명시한다.
3. **경계 조건:** 비슷한 다른 요청과 헷갈리지 않도록 "~는 다른 스킬이 맡는다", "~에는 쓰지 않는다"를 적는다. 없으면 과발동한다.

**주요 사용 사례를 먼저 입력한다.** 가장 자주 쓰일 상황을 description 맨 앞에 적고, 부가 사례와 경계 조건은 그 뒤에 잇는다. 용도가 매칭 판단의 가장 큰 단서이고, description이 잘리거나 줄어들 때도 핵심 용도가 앞에 있어야 남기 때문이다.

```
✕ description: 커밋 관련 스킬. 필요할 때 참고한다.

○ description: 이 프로젝트의 Git 커밋 단위/메시지 작성 규칙. 커밋을 만들거나, 여러 변경 사항을 몇 개의 커밋으로 나눌지 판단하거나, 커밋 메시지 제목/본문을 작성할 때 반드시 참고한다. "커밋해줘", "커밋 나눠줘" 처럼 직접 요청하지 않아도, git commit을 실행하기 직전이라면 항상 이 스킬을 적용한다.
```

**길이와 예산:**

- 스킬 하나의 `description` + `when_to_use`는 **1,536자 이하**. (예전 문서의 250자는 구버전 상한이다.)
- 그래도 `description`은 **250자 이하로 작성하는 것을 권장**한다. 1,536자는 상한일 뿐이고, 모든 스킬의 description이 세션마다 상시 로드되며 아래 전체 예산을 나눠 쓰기 때문이다.
- 전체 스킬 목록은 컨텍스트 윈도의 약 1% 예산을 공유한다. 넘치면 **호출이 적은 스킬의 description부터 통째로 드롭**되고, 디버그 경고로만 조용히 알려진다.
- 한국어는 어절 수가 아니라 **문자 수**로 센다.
- Layer 1(프론트매터)은 세션마다 상시 로드되므로 짧을수록 좋다.

## 스킬 / 에이전트 / CLAUDE.md 구분

| 구분      | 담는 것                         | 위치                             |
| --------- | ------------------------------- | -------------------------------- |
| CLAUDE.md | 항상 지켜야 하는 짧은 정적 규칙 | 프로젝트 루트                    |
| 스킬      | 재사용 절차·워크플로 ("어떻게") | `.claude/skills/{name}/SKILL.md` |
| 에이전트  | 독립 역할·권한을 가진 실행 주체 | `.claude/agents/{name}.md`       |

- 위치는 **디렉터리 + SKILL.md** 구조여야 한다. `commit-message.md`처럼 단일 파일로 만드는 것은 자주 틀리는 실수다. 디렉터리여야 상세 내용을 보조 파일로 분리해 같은 폴더에 둘 수 있다.
- 저장 범위: 프로젝트 `.claude/skills/` (리포지토리로 팀 공유), 개인 `~/.claude/skills/` (내 모든 프로젝트), 하위 디렉터리 `<subdir>/.claude/skills/` (그 디렉터리 작업 시 로드).
- 일반 절차 스킬은 "누가 언제 참여하는가" 같은 팀 전체 오케스트레이션까지 떠안지 않는다. 스킬은 "어떻게"를 정의하는 단위이고 "누가 언제"는 다른 층위의 일이기 때문이다. 조율 자체가 목적인 메타스킬만 예외다.

## 스킬 콘텐츠 유형

- **참고 콘텐츠:** 코딩 컨벤션, 아키텍처 패턴 등 작업 중 인라인으로 참조하는 지식. 사용자가 매번 `/name`을 치지 않아도 작업 중 필요할 때 적용돼야 하므로 모델이 자동 호출하도록 둔다.
- **작업 콘텐츠:** 배포, 커밋, 코드 생성 같은 단계별 워크플로. 의도치 않은 실행이 부담되면 `disable-model-invocation: true`를 붙여 `/name`으로만 실행되게 한다.

## 프론트매터

| 필드                          | 설명                                                                   |
| ----------------------------- | ---------------------------------------------------------------------- |
| `name`                        | `/` 메뉴·호출에 쓰는 이름. 기본값은 디렉터리명                         |
| `description`                 | 역할과 사용 시점. 자동 호출 판단의 핵심 기준                           |
| `when_to_use`                 | 추가 트리거 문구·맥락. `description`과 합쳐 1,536자까지만 유지된다     |
| `disable-model-invocation`    | `true`면 자동 트리거 차단, 사용자가 `/name`으로 호출할 때만 실행       |
| `user-invocable`              | `false`면 `/` 메뉴에서 숨기고 Claude만 필요 시 호출                    |
| `allowed-tools`               | 이 스킬 실행 중 승인 팝업 없이 허용할 도구 (**공백 구분**)             |
| `disallowed-tools`            | 이 스킬 실행 중 사용을 금지할 도구                                     |
| `model` / `effort`            | 스킬 활성화 시 모델(sonnet, opus, haiku, inherit) / 노력 수준          |
| `context: fork`               | 독립 서브에이전트 컨텍스트에서 실행. `agent`, `background`와 함께 사용 |
| `paths`                       | 지정한 Glob 패턴의 파일을 작업할 때만 자동 로드                        |
| `shell`                       | 동적 셸 주입에 쓸 셸 (`bash` 또는 `powershell`)                        |
| `argument-hint` / `arguments` | 자동완성 힌트 / 위치 인자에 붙일 이름 목록                             |

**자주 틀리는 점:** 에이전트는 `tools`(쉼표 구분), 스킬은 `allowed-tools`(공백 구분)를 쓴다. 두 필드명을 혼동하는 것은 자주 틀리는 실수다.

## 본문 작성 원칙

- **Why-First:** "절대 ~금지", "반드시 ~할 것"만 나열하지 않는다. 규칙 뒤에 **이유(왜냐하면)**를 붙인다. 이유를 알아야 Claude가 처음 보는 예외 상황에서도 규칙의 의도에 맞게 판단하고, 불필요하게 우회하지 않는다.
- **컨텍스트 절약 3원칙:**
  1. Claude가 이미 아는 내용(언어 기본 문법 등)은 쓰지 않는다.
  2. 없으면 실수하는 프로젝트 특수 규칙·도메인 지식만 남긴다.
  3. 긴 설명 대신 구체적인 예시 1개를 쓴다. 예시 하나가 기대하는 형태를 한 번에 전달하고 컨텍스트도 덜 쓴다. (`✕`/`○` 대비 예시가 효과적이다.)
- **어조:** "~합니다"가 아니라 **"~한다", "~하라"** 명령형으로 쓴다. 이 프로젝트의 기존 스킬(`git-commit-convention` 등)과 문체를 맞춘다.
- **마지막에 체크리스트:** 적용 직전에 점검할 항목을 번호 목록으로 둔다. 기존 스킬들이 이 구조를 따른다.
- **지속적으로 강제해야 하는 규칙**은 스킬 본문이 아니라 hooks로 옮긴다. 대화 압축(`/compact`) 중 지침이 드롭될 수 있으니 핵심 지침은 SKILL.md 최상단에 둔다.

## Progressive Disclosure: 3층 구조

| 층      | 역할             | 실제 위치                               | 로드 시점                       |
| ------- | ---------------- | --------------------------------------- | ------------------------------- |
| Layer 1 | 호출 여부 결정   | 프론트매터 (name, description)          | 세션 시작 시 상시               |
| Layer 2 | 실행 절차·라우팅 | SKILL.md 본문 (**500줄 이하**)          | 스킬이 호출됐을 때만            |
| Layer 3 | 상세 레시피·참고 | `references/`, `workflows/`, `scripts/` | 해당 조건이 맞을 때만 선택 로드 |

**"본문은 메뉴판, references는 레시피."** 아래 신호가 보이면 `references/`로 분리한다.

1. 본문이 500줄에 가까워진다.
2. 도메인 분기가 생긴다. ("매출이면 A, 재고면 B")
3. 조건부로만 필요한 상세 참조 링크가 필요하다.

분리한 파일은 본문에서 **언제 읽어야 하는지** 조건과 함께 링크한다. 조건 없이 링크만 있으면 Claude가 읽을 시점을 판단하지 못한다.

```
.claude/skills/my-skill/
├── SKILL.md          # 개요·라우팅·필수 지침
├── reference.md      # 상세 API 문서 (필요할 때만)
├── examples.md       # 코드 예시 (필요할 때만)
└── scripts/helper.py # 직접 실행할 스크립트
```

## 인자와 동적 주입

치환 변수는 스킬 본문에서 아래처럼 쓴다.

| 변수                    | 값                                   |
| ----------------------- | ------------------------------------ |
| `$ARGUMENTS`            | 전달받은 인자 전체                   |
| `$ARGUMENTS[N]`, `$N`   | 0부터 시작하는 위치별 인자           |
| `$name`                 | `arguments` 프론트매터에 지정한 이름 |
| `${CLAUDE_SESSION_ID}`  | 현재 세션 ID                         |
| `${CLAUDE_EFFORT}`      | 현재 노력 수준                       |
| `${CLAUDE_SKILL_DIR}`   | 스킬 디렉터리 경로                   |
| `${CLAUDE_PROJECT_DIR}` | 프로젝트 루트 경로                   |

**동적 맥락 주입:** `` !`git diff HEAD` `` 처럼 `!` 뒤에 셸 명령을 쓰면(여러 줄이면 ` ```! ` 코드 블록) Claude에게 전달되기 전에 명령이 실행되고 결과가 프롬프트에 들어간다. 설정에서 `"disableSkillShellExecution": true`이면 셸 실행이 거부된다.

## 안티패턴

이유와 해결 방법은 각 항목의 해당 섹션을 따른다. 같은 설명을 여러 곳에 반복하면 컨텍스트만 낭비한다.

- 이유 없는 규칙 나열 → "본문 작성 원칙"
- 500줄 넘는 본문 → "Progressive Disclosure"
- 부실한 description → "description 작성"
- `tools` / `allowed-tools` 혼동 → "프론트매터"
- 단일 `.md` 파일로 생성, 일반 스킬이 오케스트레이션 담당 → "스킬 / 에이전트 / CLAUDE.md 구분"

## 사용자가 직접 진행하는 작업

아래는 스킬을 작성하는 절차가 아니라 작성이 끝난 뒤의 작업이다. Claude는 직접 실행하지 않고, 작성을 마친 뒤 필요하다고 안내만 한다. 작성한 쪽이 직접 확인하면 결과가 한쪽으로 치우치기 때문이다.

### 검증

스킬을 쓰고 나면 실제로 유용한지 확인한다.

- **With / Without 비교:** 같은 프롬프트·모델·도구 설정에서 스킬이 있을 때와 없을 때의 품질, 속도, 토큰 소모를 비교한다.
- **트리거 테스트:** 발동해야 하는 요청(should-trigger) 8~~10개와, 비슷하지만 발동하면 안 되는 요청(should-NOT-trigger) 8~~10개를 **함께** 시험한다. 전자만 보면 과발동을 놓친다.
- 공식 `skill-creator` 플러그인으로 `evals/evals.json`(테스트 프롬프트·기대 동작)을 정의하고, 격리된 서브에이전트로 각 케이스를 돌려 `grading.json` / `benchmark.json`으로 판정·비교할 수 있다. description 자동 튜닝도 지원한다.

### 문제 해결

| 증상                            | 확인할 것                                                                                                                                       |
| ------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------- |
| 스킬이 발동하지 않는다          | description에 사용자가 실제로 쓰는 키워드가 있는가. `/skills`, `/context`로 등록 여부 확인. YAML 오류면 `--debug` 또는 `claude plugin validate` |
| 너무 자주 발동한다              | description을 구체화하고 경계 조건을 추가. 그래도 과하면 `disable-model-invocation: true`                                                       |
| 중간에 지침 이행이 멈춘다       | "본문 작성 원칙"의 hooks·최상단 배치 항목을 따른다                                                                                              |
| description이 잘리거나 사라진다 | 스킬이 많아 전체 예산(컨텍스트의 1%) 초과. `/skill-doctor`로 미사용 스킬을 찾아 `skillOverrides`에서 `"name-only"` 또는 `"off"` 지정            |

## 적용 시 체크리스트

스킬을 완성하기 전 아래를 점검한다:

1. `.claude/skills/{name}/SKILL.md` 디렉터리 구조인가? `name`이 디렉터리명과 맞는가?
2. description이 동사 나열 + 트리거 상황 + 경계 조건을 모두 갖췄는가? `description` + `when_to_use`가 1,536자 이하인가? (문자 수로 센다)
3. 도구 필드가 `allowed-tools`(공백 구분)로 쓰였는가? (`tools`와 혼동하지 않았는가)
4. 규칙마다 이유가 붙어 있는가? Claude가 이미 아는 내용은 빠졌는가?
5. 어조가 "~한다/~하라" 명령형인가?
6. 본문이 500줄 이하인가? 분기·조건부 상세는 `references/`로 분리하고 읽을 조건을 적었는가?
7. 지속 강제가 필요한 규칙은 hooks로, 항상 적용되는 짧은 규칙은 CLAUDE.md로 보냈는가?
8. 작성을 마친 뒤 "사용자가 직접 진행하는 작업"(검증, 문제 해결)을 사용자에게 안내했는가? Claude가 직접 실행하지 않았는가?
